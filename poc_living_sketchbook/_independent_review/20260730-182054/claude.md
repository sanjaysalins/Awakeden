## Independent review — Fable round 6: THE KEEPER

I checked this against the actual POC source (`poc_living_sketchbook/storm/_keeper_poc/_build_poc.py`, `_bold_poc/_build_bold.py`, `_vault_poc/_build_vault.py`, `_vault2_poc/_build_vault2.py`), the verdicts file, and `.claude/skills/living-sketchbook/SKILL.md`. The verdict tally (9 keep / 13 kill, 22 total) and the LAW 2 scale numbers (`BOLD = 1` in `_build_poc.py:42`, `pencil_study(..., contrast=1.9/2.3)` in `_build_poc.py:311-312`) are real and already in the code — that part of the plan is accurate.

**1. "Promote, don't rewrite" understates the actual work and risks the production engine drifting from what the user just approved.**
Several behaviors the plan describes as reusable, parametrized API surface are currently hand-keyframed, scene-specific closures:
- `starve=(n_glyphs, blot_xy)` — in the real POC (`_vault_poc/_build_vault.py:257-286`) the starve is a hardcoded 5-value alpha falloff `[200,150,105,65,38]` and manually-placed blot coordinates (`bx, by`) tuned to one still (`s02_water.png`). There's no formula to "promote" — a falloff function has to be designed from scratch.
- `interrupt_at=t` — the POC (`_vault_poc/_build_vault.py:117-133`) is a hardcoded `T_WORD = 3.0` filter on `entry_events` output for one specific still. Turning that into a clean class parameter is new design.
- Candle-Only's claimed "R(t) is energy-driven inverse" (engine 5) — the actual POC (`_vault2_poc/_build_vault2.py:239-247`) has `R_of(t)` hand-keyframed to fixed timestamps (0.8s/2.4s/5.2s) picked for one demo clip. It is **not** driven by `held_breath`'s energy envelope at all today — "energy-driven" is a new design decision being introduced at promotion time, not something the user's taste-gate actually saw.
- Torn-Out Page (`_bold_poc/_build_bold.py:177-222`) similarly hardcodes `GRAB/RIP/GONE` timestamps and deckle geometry to one specific still pair.

None of this is disqualifying, but the plan's framing ("promote the proven POC engine... keep seeds so the approved POC looks are reproducible") implies low-risk extraction. It's actually a generalization/redesign of four independent, throwaway scripts into one class-based API (`KeeperEntry`) — real risk the generalized version won't look like what was just KEEPed. Nothing in the build order re-validates the generalized behavior against the *specific* approved POC clips before lock — step 2's "demos on real Storm spreads" should explicitly include a side-by-side against the original POC outputs (`keeper_A_panic_entry.mp4`, `vault_1_word_whole.mp4`, `vault_4_inkwell.mp4`, `v2_05_candle_only.mp4`) to catch drift, not just fresh demos.

**2. `page_transitions.py` smuggles two never-built, never-approved devices into a v1 deliverable alongside the one proven device.** The user's verdict approved exactly "The Torn-Out Page," with a loose note ("we can have more such transition effects built in") that opens a lane — it is not approval of `slide_under`/`lift_away` specifically, which have zero POC minutes behind them. This project's own standing pattern is POC-first / bake-off-before-build (`poc-prompt-author-bakeoff`, `feedback-test-gate-before-batch`) — exactly for cases like this. Bundling two speculative designs into the same engine and gating them with the same generic "user eye gate" as the proven device risks spending build effort on something that gets killed, same as 13 of the 22 already were.

**3. LAW 1's letter-by-letter revision changes a currently-locked, universal rule with no stated retroactivity policy.** `SKILL.md:142-144` states Scribed Ink verses are "letter-by-letter" as a universal rule for **all** KJV text on the page. The plan restricts that to narration-voice verses only and gives Christ's words whole-arrival — self-flagged as "pending panel," which is good, but the doc never says whether the already-produced Storm episode / `AT_THE_DOOR_sketch_poc` need re-review under the new rule or are grandfathered. This project has an explicit precedent for stating that (the 3.0s landing-hold change: "not retrofitted... only new pieces are held to"). This plan should say the same thing one way or the other.

**4. The flagship engine's governors (≤1 entry/spread, ≤4 entries+1 header/episode, "never doctrine claims") have no deterministic backstop, unlike almost everything else this project governs.** Every other content-safety rule in this repo pairs LLM/panel judgment with a fail-closed `$0` script (`narration_gate.py`, `panel_variety_lint.py`, `render_lint`/`verify.py --gate`). Engine 1's self-test list (jitter, byte-stability, alpha monotonicity, interrupt behavior) is all rendering-mechanics — none of it enforces the entry caps or checks for doctrine-adjacent phrasing slipping into free-form Keeper marginalia, which is new *prose content* on the finished frame, not just a visual effect. Given the project's NON-NEGOTIABLE doctrine-both-ways rule, this is the one place a cheap deterministic count/keyword governor is clearly warranted before the panel step, not instead of it.

VERDICT: REVISE
TOP FIXES:
1. Before building engine 1/3/5's generalized APIs, re-render the generalized version against the exact approved POC clips (keeper_A, vault_1, vault_4, v2_05) side-by-side and require a fresh user eye-check on those specific pairs — don't let "looks similar on new demos" stand in for "matches what was approved."
2. Split `slide_under` and `lift_away` out of the v1 `page_transitions.py` deliverable into their own quick POC/taste-test round before folding them into the production engine; ship only `torn_out` (the one actually approved) in v1.
3. Add a deterministic $0 governor script for the Keeper voice caps (≤1/spread, ≤4+header/episode, flags verse-card collisions) alongside the panel review, and state explicitly whether the LAW 1 letter-by-letter revision retrofits already-shipped pieces or only applies forward.
