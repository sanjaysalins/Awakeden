## 2. Feasibility / codebase assumptions

**“ONE finality rule” is not absolute.**  
Problem #1 lists four callers; the design claims one rule. Live `upload_engine._find_video` still has **last-resort fallbacks** (uncaptioned `viral_cut.mp4` / any non-bak long mp4) after calling `finality.final_video`. Upload kits can still pick a different “final” than the gate. The plan never says whether those fallbacks stay or die.

**Freshness anchor is not one sha.**  
Opening of “Freshness chain”: *“The final video's content sha256 is the anchor.”*  
But read frames are cut from `*_scored.mp4` (`build_readpage.py`), and G5 compares `_meta.source_sha` to **scored**, not SFX final. G3/G4/G6 use **final**. Two anchors, one sentence. Operators will mis-debug “final changed, read still green / scored changed, final green.”

**`build_readpage` only stamps `_meta` when frames are written.**  
```python
if wrote:
    ... write _meta.json
```  
Skip-extract path leaves old/missing `source_sha`. Plan says frames always record source sha; gate WARN can be permanent noise or silent miss. Plan does not require stamp-on-every-run or use of `finality.content_sha`.

**G7 under-delivers the plan text.**  
Plan: *“parent exists and is a long”*.  
Code only checks: (a) if cluster has a long, parent must equal that long; (b) parent slug exists in catalogue. **It does not require `kind == "long"`.** A short can `parent:` another short and pass if no long sits in that cluster.

**G5 “read page built for promoted items” is soft.**  
Table implies a real site obligation. Code: live without read page = **WARN** only; studio_complete with no page = no finding. “Promoted” is undefined. Either raise to FAIL for `live` or stop advertising “built for promoted items.”

**G6 biconditional is incomplete.**  
Plan: `youtube_id ⟺ public_status: live ⟺ dated ledger entry with URL`.  
Code FAILs several legs, but **ledger youtube entry without `youtube_id` / not live** is not fully closed; missing `posted` is WARN not FAIL. “Dated” is not FAIL-closed as written.

**Orphan scan is batches-only.**  
`gather()` orphans = `batches/*/*/piece.json` not joined. Longform / pilot / other layouts never appear as orphans. Plan’s “catalogue is the registry” still allows shadow inventory outside batches.

**No tests.**  
Zero `test_*.py` hits for `release_state` / `finality` / `upload_tracker` / SYNC-G*. Plan has no verification section. For a gate that fails closed on ship, that is a real hole.

## 3. Hidden risks / single points of failure

**Post-ship re-render → permanent RED until full re-upload.**  
G6 FAILs when posted `final_sha != current final`. Correct for truth, brutal in ops: any SFX re-lay on a LIVE piece forces re-post **all** platforms. Plan only softens sha churn for G5 (audio-only sfx). Same class of change on final is hard FAIL with no “ack outdated upload” / “posted is intentionally older” path.

**`upload_tracker` rewrites whole `manifest.yaml` via `yaml.safe_dump`.**  
One write path is good; dumping the whole catalogue is a SPOF: comment loss, key reorder, race with hand-edits, partial write risk. Plan never requires atomic write or surgical field patch.

**`.sha_cache.json` is unlocked shared mutable state.**  
Parallel board + gate + publish can interleave cache writes. Silent corruption → wrong freshness until cache clear. Plan treats cache as free lunch.

**Dual gates, no operator map.**  
`publish_check` already does pack `final_sha` + UK-G1..G7. `release_check` does catalogue-level SYNC-G1..G7. Plan never says: **when pack-level vs desk-level**, who runs which before deploy, and that both can RED for the same stale pack. Risk: people run the green one and ship.

**Multi-platform tracking is YouTube-first in practice.**  
Ledger supports tiktok/fb/ig, but only YT flips `public_status: live` and rebuilds read pages. “TO-POST queue” for non-YT is fine; “published coherence” is still YT-shaped. Plan sells four platforms; site “live” still means YouTube.

## 4. Missing steps / edge cases

**No migration / bootstrap section.**  
If this were greenfield, first `release_check` would RED half the catalogue until: `source:` backfill, pack re-stamp, thumbs `_meta`, ledger seed for already-posted URLs, `parent:` on cluster shorts. STATE claims much of that was done — **the plan itself does not sequence it**. Design-without-migration is how desks die on day one.

**No conflict policy for hand-set `youtube_id`.**  
Only `upload_tracker` “should” write ledger, but anyone can edit manifest. G6 catches some skew; plan does not forbid direct manifest youtube edits or define repair.

**Multiple `*_sfx.mp4`.**  
`finality` takes `sorted(hits)[0]` — deterministic but arbitrary. Plan never says “exactly one sfx final” or FAIL on ambiguity.

**Caption policy is load-bearing and almost invisible.**  
Final = sfx for living-page is a 2026-07-08 policy. Plan’s G2 (“have a final”) depends on it; without stating it, “FINAL” looks like marketing language.

**Board “nested under long” is sort order, not nesting.**  
Plan: *“shorts nested under it, so one glance.”* Implementation sorts by cluster/parent; HTML is a flat table. Over-sold UX.
