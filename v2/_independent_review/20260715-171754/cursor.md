# Independent review — cursor (OK, 230s)

Independent adversarial review of the RELEASE SYNC plan, checked against the repo (including a live `release_check.py` run: **7 FAIL, 28 WARN** on 60 catalogue items).

---

## Feasibility vs codebase

**Most of the stack exists and runs**, but the plan overstates completeness and misdocuments a few APIs.

- **Problem #1 is fixed in code, but the plan reads like an open wound.** The four divergent `final_video` implementations are consolidated into `pipeline/finality.py`; callers (`publish_pack`, `upload_engine`, `thumbnails`, `release_state`) import it. The problem statement is valid history, not current architecture.
- **API mismatch:** the plan says `final_video(dir, kind)` (line 33), but the implementation is `final_video(piece_dir)` with **auto-detected layout** — no `kind` parameter. Anyone scripting against the plan will call a nonexistent API.
- **Phantom command:** Standing rule says the board is regenerated by `release_check.py --board` (line 111). `release_check.py` only exposes `--slug` and `--strict`. There is no `--board`.
- **Ledger file doesn't exist yet.** Code expects `data/release_ledger.json`; it is not on disk until the first `upload_tracker.py --set`. The plan presents the ledger as live infrastructure; it's schema-only until first use. No backfill/migration step for anything already posted.
- **`release_check` is not in `/validate`.** The plan says it "joins `validate` in the pre-ship set" (line 109). `pipeline/validators.py` has zero references to `release_check` or `release_state`. There are also **no `test_release*` / `test_finality*` tests**. The gate is manual policy, not enforced teeth.

## Hidden risks and false assumptions

### 1. "One registry, one hard join" — still multi-path drift

The plan claims SYNC-G1 kills fuzzy matching via `source`/`read_source`/`study_source` (line 67). **`resolve_source()` picks the first field that exists** — `source` → `read_source` → `study_source` — and ignores the others.

That leaves a seam the plan says it eliminates:

| Slug | `source` | `study_source` |
|------|----------|----------------|
| `ps22-02-mockers-words` | `../batches/.../mockers_words_ps227` | `../v2/pilot/mockers_words_ps22/v1` |
| `zechariah-12-10-pierced` | batch lane | pilot lane |

`build_catalog.py` reads **`study_source` directly** for study figures. `release_state` / SYNC-G2–G4 check **`source`**. No gate verifies those paths match, or that `study_source` even exists / is fresh. **Problem #5 (three inconsistent encodings) is narrowed, not solved.**

Same class of bug for read pages: `build_readpage.py` uses **`read_source`**, but SYNC-G5 freshness compares `_meta.source_sha` against a video resolved from **`source_dir`** (via `resolve_source`), not necessarily `read_source`. Works when they match; silently wrong when they diverge.

### 2. Freshness chain mislabels the read-page anchor

Lines 52–58 say every derived surface records **"the sha of the final it was built from."** That is **false for read frames**:

- Publish pack / thumbs / posting ledger → `*_sfx.mp4` (the postable final) ✓  
- Read frames → `*_scored.mp4` via `build_readpage.py`, field `source_sha` ✓  

The plan partially walks this back in the SYNC-G5 row ("audio-only sfx change also shifts the sha"), but the **Freshness chain section contradicts its own gate design**. Operators following line 52 will expect read-page staleness to track the SFX final; it doesn't.

Worse: `_meta.json` is only rewritten when **new frames are extracted** (`if wrote:` in `build_readpage.py`). Re-rendering the scored source without `--force` can leave a stale `source_sha` while G5 only **WARN**s.

### 3. "ONE write path" is overstated

- **Ledger:** only `upload_tracker.py --set` writes it — true.
- **Manifest:** `upload_tracker.py` also writes `youtube_id` + `public_status: live` on YouTube `--set`. But manifest is also manually edited, merged via `_website/import_catalogue.py`, and consumed by multiple builders. **YouTube live-state lives in manifest; TikTok/FB/IG live only in the ledger.** SYNC-G6 only enforces tight coherence for YouTube. Cross-store drift for non-YT platforms is possible if manifest fields are added later without ledger sync.

### 4. Finality rule has silent ambiguity

`finality.final_video()` returns **`sorted(hits)[0]`** when multiple `*_sfx.mp4` files exist. The plan doesn't mention tie-breaking. A rollout that parks old finals beside new ones (even non-`.bak`) can pick the wrong file **without FAIL**.

### 5. Orphan detection is batch-only

Orphans are discovered via `batches/*/*/piece.json`. **Longform lanes have no `piece.json`** and won't appear as orphans. A longform folder missing from the manifest won't be surfaced by SYNC-G1's orphan WARN path.

### 6. G7 / `parent:` solves one cluster, not the general long↔short problem

`parent:` exists on **8 psalm-22 shorts only**. Cross/resurrection shorts (`cluster-01-cross`, etc.) have **no `parent:`** and no catalogue long to link to. Problem #5's "authoritative link" claim is **true for ps22 only**; other clusters still rely on folder naming / `cluster` strings with no gate.

## Over-engineering / premature build

- **Dual gate systems with duplicated freshness logic:** `publish_check.py` (UK-G1–G7 + `final_sha`) and `release_check.py` (SYNC-G1–G7 + `final_sha`) both stamp-check packs. The plan sells "one gate" but Stage 6 still has a separate per-pack GREEN gate. Workflow ambiguity: which must pass before posting? Both? If `publish_check` is GREEN but `release_check` FAILs, the plan doesn't say.
- **Board + gate + ledger + sha cache + 7 SYNC gates** before any piece is actually posted (all `youtube_id: null`, ledger empty). Reasonable given the 14-stale-pack incident, but **28 WARNs on first run** suggest the gate will be noisy operational friction until catalogue hygiene catches up — the plan doesn't budget that migration work.
- **`data/.sha_cache.json`** (untracked) adds a shared mutable cache with **no file locking**; parallel thumbnail + publish + gate runs can race on the cache file.

## Reuse

**Good reuse:** `finality.py` centralization, `release_state.gather()` shared by board and gate, `thumbnails.py` driven off manifest via `release_state` — no duplicate hardcoded episode lists.

**Bad reuse / duplication:**

- Freshness checking exists in **both** `publish_check.check_unit()` and `release_state.run_gates()` — same `final_sha` logic, two entry points.
- `build_readpage.py` reimplements sha256 inline instead of calling `finality.content_sha()` — same hash, different cache path; inconsistent performance/invalidation behavior.

---

## Cost / spend

The **$0 deterministic gate model is justified** — this directly prevents the silent stale-pack failure (commit 9007339). No metered spend introduced.

Cost is **operator time**: mandatory refresh cascades (re-render final → `cli_publish.py` → `thumbnails.py` → `cli_publish.py` again → `build_readpage.py` → `release_check.py`) are implied but never spelled out as a ordered checklist. One missed step leaves WARN/FAIL noise or, worse, a false GREEN on read pages (WARN-only staleness).

---

## What the plan gets right

- Sha-anchored staleness instead of mtime alone — correct lesson from dyncam.
- Hard join killing fuzzy letter-match — verified gone from `release_state`; the ew-jonah class of bug is addressed for the primary join path.
- Human paste URL workflow (`upload_tracker --set`) — matches HF-POC discipline; no premature auto-upload.
- TO-POST queue not FAIL-ing unposted platforms — sensible separation of "ready" vs "posted."
