everything already built** — Stages 0, 1, 1b, 3b (SFX), 4 (caption

## 6. STAGE 2 — VISUAL: comic-strip-native (the technique this document exists to integrate)

This is the stage the whole document is built around. Full technical detail
lives in `COMIC_STRIP_NATIVE_SPEC.md` — this section sequences it into the
pipeline and adds the pipeline-level decisions the spec itself explicitly
leaves open (§9-§10 there).

### 6a. Page-count mapping to the locked narration structure (PROPOSED, UNTESTED)

Today's validated recipe used exactly 3 pages for a 3-movement story
(Penitent Thief). No piece has ever been built by deliberately mapping pages
onto the Gospel Five-Beat structure — `COMIC_STRIP_NATIVE_SPEC.md` §10 item 3
says outright that "full end-to-end assembly... has never been assembled."
**Proposed starting default**, to be confirmed or discarded after the first
real attempt: 1 page per 1-2 narration beats, so a standard 5-beat short
maps to roughly 3 pages —

```
Page 1  ≈ Hook + Point   (0-18s)
Page 2  ≈ Proof + Conviction   (18-52s)   — usually the densest page; the
                                              KJV-quote beat lives here
Page 3  ≈ Landing   (52-60s)   — the gospel-pivot page; carries the hero close
```

This happens to match today's 3-page test by coincidence of scale, not
because the mapping was deliberately designed against the structure. **Treat
this as the starting hypothesis for the first production attempt, not a
locked rule** — a Proof beat that is unusually dense (a long KJV quote plus a
steel-manned objection) may need its own page.

### 6b. The Master Comic Blueprint (existing technique, cited not duplicated)

Full template and validated wording: `COMIC_STRIP_NATIVE_SPEC.md` §1.2. In
order: Core Aesthetic Blueprint (frozen, reused verbatim every page) → Global
Textual Constraint (no baked text) → Character Design Anchors (every named
figure, written BEFORE panel content, reused verbatim page-to-page, carrying
the Christ body gate §2a and the canonical-wording rule §2b explicitly and
REPEATEDLY — a first-pass render can still drift even when the rule is
understood, confirmed twice now including the 2026-07-25 reproducibility
re-test, spec §1.4) → Panel-by-panel spec (Scene Type / Composition /
Lighting per panel, closing with a redundant style/no-text restatement).

**Write the Character Design Anchors using the fact cards from Stage 0.5,
not from memory.** This is a genuine, buildable near-term hardening this
document proposes: the existing `pipeline/bible_kb.py` fact-card discipline
(specified/constrained/free) already exists for the single-image scene-plan
lane; nothing stops a comic-strip-native piece's panel-by-panel spec from
being written against the SAME derived fact cards before generation, and
checked against them after (a text-level version of BC-G1/BC-G2, today
manual — see §10 Open Items for the deterministic-gate proposal).

### 6c. Generation + chaining

`hf generate create nano_banana_pro --prompt "..." [--image <prev_page.png>]
--aspect_ratio 9:16 --resolution 2k --wait` — page 1 has no `--image`; every
later page chains to the immediately preceding page (`COMIC_STRIP_NATIVE_SPEC.md`
§1.3). If an early page drifts from where later pages converged, re-roll it
chained BACKWARD to the later page, not from scratch (validated once, spec
§1.3).

### 6d. Full-resolution eye-check QC — the cheap gate (CSN-G1..G4)

Every item is human-eye-only today (`COMIC_STRIP_NATIVE_SPEC.md` §7):

| Gate | Checks |
|---|---|
| CSN-G1 No baked text | zero letters/lettering anywhere |
| CSN-G2 Character anchor fidelity | every named figure matches face/build/hair across every page |
| CSN-G3 Christ body gate | no heroic/athletic musculature, no ab-definition, no blood beyond faint brow marks, on EVERY passion-beat panel, EVERY time — §1.4's re-test proved this recurs even with "fixed" wording; never skip this because "we already fixed it" |
| CSN-G4 Canonical wording only | no apocryphal/traditional-but-non-canonical name or detail (ties directly to Stage 0.5's sweep) |

**Never a thumbnail glance — Read the actual PNG at full resolution.** This
is the cheapest point in the whole pipeline to catch a doctrine miss:
~$0.40/page vs. the cost of an animated clip built on a bad page.

**═══ HUMAN GATE 2 (this document's proposal, mirroring the existing
image-gate-before-Kling cost saver already locked in
`pipeline/orchestrator.py` for the old lane): approve every page BEFORE any
animation spend. Reroll/exclude here, same principle as the existing
`cli_pipeline.py --reroll` / `--exclude` at its own GATE 2. ═══**

**Cost:** ~$0.40/page at 2k, 9:16 (today's actual rate,
`COMIC_STRIP_NATIVE_SPEC.md` §8). Budget rerolls on top — nothing in that
figure assumes zero.

### 6e. Animate with intent (Kling 3.0 direct — the current best-of-tested default)

`hf generate create kling3_0 --start-image "<page.png>" --prompt "<motion
prompt>" --mode pro --sound off --duration 5 --aspect_ratio 9:16 --wait`.

**"With intent" means naming the accepted cost, not chasing a clean prompt
that doesn't exist yet.** Four prompt strategies were tried
(`COMIC_STRIP_NATIVE_SPEC.md` §5.1); none eliminated invention without also
killing the motion. The current instruction: write a motion prompt that
grants the LEAST "license to move" that still produces visible life (§5.1's
finding that invention risk scales with license granted, not with
camera-vs-static framing), then accept some invention as a real, named cost
— not a solvable prompting problem with more iteration.

A **10-model bake-off** (`COMIC_STRIP_NATIVE_SPEC.md` §5.2) ranks Kling 3.0
the best cost-to-quality tier (~$1.13-1.31/clip at 5s, real billed rate);
Grok Video 1.5 / Seedance 2.0 full are clean but 2.5-3x the price; several
others (Kling 3.0 Turbo, Veo 3.1 Lite, Seedance 1.5 Pro, Happy Horse) show
structural collapse and are avoid-entirely.

**If invention becomes unacceptable for a specific real piece** (e.g. a
sacred beat where an invented gesture on Christ is a doctrine problem, not
just an aesthetic one), the flagged next experiment is **crop-and-recomposite**
(spec §5.3): crop each panel out of an already-consistent page, animate each
independently (nothing else in frame to invent onto), then recomposite via
`panel_animator/grid_choreography.py` — **this tool already exists and is
already proven, just on a different (composited-stills) pipeline** (see
`panel_animator/README.md`: it composites separately-rendered clips into a
grid with a virtual page camera). Crop-and-recomposite is the one approach
that could reuse it directly. Reasoned through in detail, never actually run
— name it as a real decision point when a piece's stakes justify the
~$12/3-page test, not a proven fallback.

### 6f. Multi-timestamp clip QC (CSN-G5) — the second cheap-relative-to-waste gate

Extract and eyeball frames at 5 timestamps spanning the full clip (start /
quarter / mid / three-quarter / end) before calling ANY clip done — a single
glance or trusting the render-success log caught nothing real today; only
full-duration inspection did (`COMIC_STRIP_NATIVE_SPEC.md` §6 item 2:
real failures caught this way included a forced-loop clip motion-dead across
all 5 samples, a silent panel duplication, and an invented mid-clip panel).

**═══ HUMAN GATE 3 (this document's proposal): approve every animated clip
before build. ═══** Mirrors the existing clips gate at the end of
`cli_pipeline.py`'s three-gate model.

**Cost:** ~$1.13-1.31/clip × 3 pages ≈ **$3.39-3.93** for a 3-page short's
animation layer, before reroll budget.

## 7. STAGE 3 — Build / assembly (PROPOSAL — no existing tool does this shape of job)

**This is a genuine gap, not a citation.** `cli_assemble.py` +
`pipeline/assembly_engine.py` do a JIGSAW: many short single-scene clips fit
to word-timed slots via LLM-planned speed/trim allocation (AS-G1..G9). A
comic-strip-native piece produces the opposite shape — 2-4 LONG clips, each
one already a whole 4-panel page moving together, not atomic clips to be
diced and speed-ramped into word slots.

**The much closer existing analog is the LIVING-PAGE lane**
(`v2/SPEC.md` §2L, `v2/LIVINGPAGE_STANDARD.md`): `run_piece.py` +
`build_livingpage_16x9.py` already choreograph word-timed panel arrivals
(SLAM/TAKEOVER/SACRED STILLNESS) over a `piece.json` manifest of stills+clips,
and `panel_animator/grid_choreography.py` already does a "virtual page
camera" pass over a live grid (racking focus toward whichever panel currently
holds attention, dimming the others) — exactly the move a comic-strip-native
page needs once it has 3-4 live panels in one frame simultaneously.

**Proposed shape (untested, this document's synthesis, not an existing
tool):** treat each comic-strip-native PAGE the way the living-page engine
treats one beat's panel grid — a `grid_choreography` pass timed to the
narration's word-alignment (already produced at Stage 1b) sweeps attention
across the page's live panels in narration order, landing on the panel whose
content matches the words currently spoken. **SACRED STILLNESS applies
unmodified**: a red-letter/passion panel never slams or shakes — the same
locked rule already in `v2/LIVINGPAGE_STANDARD.md` §1. The hero close
(gospel-pivot, per the existing AS-G6/AS-G7 discipline) is the final page's
climactic panel, held.

**Gate:** none of AS-G1..G9 apply as written (they assume the jigsaw's atomic
clip model). This document does NOT propose new gate names for this stage —
that is real, unbuilt work flagged in Open Items §10, not something to
invent casually here.

**Cost:** $0 (ffmpeg/PIL compositing, same as the existing living-page and
`grid_choreography` tooling).

## 9. STAGE 4 — Captions: the direct integration point (a real, engaged answer)

This is the one place today's finding and the existing system collide
directly, and the task explicitly asks for a real answer, not a dodge. Here
it is, reasoned through:

**The question:** comic-strip-native's own §3 decision drops ALL baked text
from the art — no speech bubbles, no caption boxes, nothing. The existing
`caption-policy-comic-boxes` rule says a **living-page** final skips the
WhisperX ivory overlay because *"the comic box IS the caption"* — the
living-page engine's own code (`build_livingpage_16x9.py` +
`caption_layout.py`/`caption_render16.py`) draws in-world parchment-band
captions as part of assembling the page. **Comic-strip-native has no
equivalent code layer.** The model draws a finished page with nothing left
over for code to compose a caption box around — the caption-policy rule's
PRECONDITION (a code-composited box exists to skip an overlay for) is simply
absent.

**The answer this document proposes:** a comic-strip-native piece is **not**
a living-page piece in the caption-policy sense, and should default to the
**Baroque/scene-plan lane's caption rule** — WhisperX-timed ivory captions via
`veed_io/serif_captions.py` (INV-16, "caption is the final step on every
finished clip") — **unchanged, unmodified, exactly as it runs today.** Three
reasons this is the right default, not just the only available one:

1. It is the reason comic-strip-native's §3 gave for dropping baked text in
   the first place — "the project already has a separate, working, $0
   solution for on-screen text... applied at final assembly, timed to the
   actual narration audio." Choosing anything else here would contradict the
   technique's own stated justification for its central design decision.
2. It has zero assumptions about panel/page geometry baked in — it overlays
   on a finished video regardless of what's under it, so it works whether
   Stage 3's build produces a single held page, a grid-choreography sweep, or
   anything else this document's proposal in §7 gets replaced by later.
3. It is already proven, already $0, already the standing default (INV-16).

**What is genuinely still open, flagged not decided:** whether a BESPOKE
in-world caption-box layer — a parchment band styled to match the vintage
graphic-novel aesthetic, placed panel-aware (tucked into a gutter or a
deliberately reserved quiet zone, the way `PAINTED_COMIC_SPEC.md` §6 already
reserves "in-scene negative space" for its own captions) — would look and
read better than a generic ivory lower-third sitting on top of dense ink
linework. This is plausible; **the user's own phrase "great remotion captions
for a comic book" reads as wanting exactly this.** But: (a) no such layer
exists for native multi-panel pages today (nothing tracks panel boundaries in
a comic-strip-native output the way `panel_animator/`'s tools track them for
COMPOSITED grids), (b) building it is real, unbuilt work, not a config flag,
and (c) `PAINTED_COMIC_SPEC.md`'s own prime directive uses "Remotion" for
"the code layer that draws text" in a way that may be aspirational/generic
rather than literally the paused `_remotion/` Node engine (memory
`noir-trailer-remotion-engine` describes that engine as built for one noir
trailer, not general captions) — this naming is itself ambiguous and worth
resolving before anyone commits to "build it in Remotion" literally.

**Recommendation:** ship the FIRST comic-strip-native production piece with
the WhisperX/`serif_captions.py` default, unmodified. Judge legibility over
the dense ink art by eye on that real piece. Only THEN decide whether a
bespoke panel-aware caption layer is worth building — with real evidence
instead of a guess. This is a proposal, explicitly not a certainty.

**Gate:** the existing `/caption` skill's recipe, unmodified. **Cost:** $0
(offline WhisperX + ffmpeg/libass).

- Grabs a hero FRAME from the piece's finished final video (per the ONE
  finality rule, `pipeline/finality.py::final_video()` — indifferent to
  which visual technique produced that final), at a timestamp from
  `publish_meta.json`'s `"thumb": {"t": ..., "title": [...], "ref": "..."}`
  spec, defaulting to 40% of the video's duration if unspecified.
- `blank_fraction()` auto-avoids landing the grab on unpainted canvas (a
  panel mid-slam that hasn't finished drawing in yet) by walking nearby

  specifically.
- Composes `thumb_16x9.jpg` / `thumb_9x16.jpg` / `thumb_1x1.jpg` +
  `thumb_tiktok.jpg` (centre-safe cover variant) with cover-crop, a bottom
  ink gradient, fitted title text, the verse ref, and the AWAKEDEN wordmark
  (`brand_assets()`, `compose()`, `compose_tiktok()`).
- Writes a hash-stamped `_meta.json` (`final_sha`) so `release_check.py`
  SYNC-G4 can detect staleness.

**What comic-strip-native changes here: nothing structural.** This tool
already works on ANY finished final video regardless of visual technique —
it does not know or care whether the frame under it came from a Baroque
still, a living-page grid, or a comic-strip-native page. **One concrete,
grounded recommendation specific to this technique:** with only 2-4 pages
(vs. 14-25 scenes in the old lane), the 40%-of-duration default heuristic has
much less material to land well on — set `publish_meta.json`'s `thumb.t`
explicitly to the exact timestamp of the piece's climactic page/panel (the
gospel-pivot, matching the same figure that closes the cut per AS-G6/AS-G7's
existing "hero = gospel-pivot" principle) rather than trusting the default on
a comic-strip-native piece.

**Gate:** SYNC-G4 (thumbs fresh vs. current final, `release_check.py`).
**Cost:** $0.

## 14. The character/world-bible persistence gap — the single most important open item

This deserves its own section, not a bullet, because it is the gap that
decides whether comic-strip-native can ever be more than a one-off technique.

**What's proven today:** character consistency WITHIN one piece — page N
chained to page N-1 via `--image`, holding a figure's appearance across 2-3
pages of the SAME story. Rock-solid when the figure has strong distinguishing
detail (Goliath's armor); weaker on plain figures (the Penitent Criminal's
face drifted).

**What's NOT proven, at all:** whether Jesus (or any recurring figure) looks
like the SAME MAN across TWO DIFFERENT PIECES. Nothing in today's testing
ever generated a comic-strip-native page for a second story and checked it
against the first. This is a completely different, harder problem than
page-to-page chaining within one narrative.

**How the EXISTING single-image pipeline already solves this, for
comparison:** `pipeline/visual_render.py`'s `NBPProvider` attaches a locked
`ref_jesus_<variant>.png` from `nano_banana_pro_batch_output` on every
relevant scene, across every piece that uses it — one small set of locked
reference IMAGES, reused by attachment, not by re-describing Jesus in prose
each time. `locked-stills-provider-split` (memory) already establishes this
as the working answer for that lane: NBP handles Christ/face consistency via
reference attachment; HF handles neutral plates.

**Comic-strip-native has never been tried against a locked EXTERNAL
reference image — only page-to-page self-chaining within one piece.** This
is the concrete gap, stated precisely: `--image` today always points at "the
piece's own previous page," never at a pre-existing, cross-piece-locked
portrait.

**The concrete next experiment this document proposes** (untested — a
hypothesis, not a claim): take an existing locked `ref_jesus_<variant>.png`,
or a newly-approved comic-strip-native portrait treated as a locked anchor,
and pass it as `--image` for comic-strip-native's PAGE 1 (instead of leaving
page 1 with no reference, as today's recipe does). Test whether
`nano_banana_pro`'s chain mechanism holds fidelity when the reference is a
single portrait/still rather than a same-technique previous page. This
directly tests whether series-scale reuse is possible at all.

**A second-order problem to expect even if that works:** a single reference
image can't cover every register a real series needs — passion Christ,
teaching Christ, risen Christ are visually different scenes, the same way
the existing pipeline already needs multiple `ref_jesus_<variant>` files, not
one. **Proposed shape (this document's synthesis, clearly a proposal, not a
finding):** a small "Character Anchor library" — a handful of LOCKED
Character Design Anchor TEXT BLOCKS (not just images) per recurring figure
per register, reused verbatim across pieces the same way the Aesthetic
Blueprint is already reused verbatim across pages of ONE piece — optionally
paired with a locked reference image per register for the `--image` chain.
Building this is real, unbuilt work; it does not exist today in any form for
this technique.

**Why this gets real weight, not a footnote:** without it, comic-strip-native
stays a one-piece-at-a-time technique — usable, but not a series identity.
Every downstream promise in this document (visual-world clustering in §2,
"cluster the first several pieces together" recommendation) exists BECAUSE
this gap is open, not despite it. Resolve this before treating
comic-strip-native as more than a validated one-off.

## 15. Reuse-first discipline — does it apply here?

**Honest answer: not cleanly, and this document does not force it to.**
INV-19 ("library reuse is topical-fit-gated AND clean-gated") governs reusing
an existing RENDERED ASSET (a still or clip) across pieces when a
topically-matched one already exists. Comic-strip-native pages are, by
design, bespoke multi-panel compositions built for one specific narration's
specific beats — there is no meaningful sense in which a Penitent Thief page
could be "reused" for a different story's different beats the way a neutral
crowd-scene plate can be.

**The reuse that DOES apply here is a different kind: prompt-TEXT reuse, not
asset reuse.** The Aesthetic Blueprint block and (per §14 above, once built)
a locked Character Anchor block are reused VERBATIM — this is real reuse
discipline, just operating on prompt text rather than rendered pixels. Don't
force INV-19's asset-reuse frame onto this stage; name the difference
explicitly instead, as this section does.

## 16. Cost / spend discipline — POC mode vs. production mode

**Today's exploration was deliberately expensive, and that was correct, not
wasteful.** `COMIC_STRIP_NATIVE_SPEC.md` §8 records **$37.36** spent across a
full day systematically testing prompt strategies, chaining protocols, 10
animation models, and (in the two follow-up findings folded into that spec
today) a reproducibility re-test and a 5-model image bake-off. That is what
`feedback-test-gate-before-batch` and `ask-before-spending` (INV-20) are FOR —
paying to learn the recipe once, deliberately, before ever running it at
production scale.

**A PRODUCTION run following the validated recipe should cost far less** —
per `COMIC_STRIP_NATIVE_SPEC.md` §8's own planning number, restated and
extended here to the WHOLE piece, not just the visual layer:

| Line | Cost | Basis |
|---|---|---|
| Narration (Opus planning) | ~$5-6, or $0 in agent-mode | existing cost model, `v2/SPEC.md` §7 |
| Audio (ElevenLabs) | ~$0.50 | existing cost model |
| Comic pages, 3 pages @ $0.40 | ~$1.20 | `COMIC_STRIP_NATIVE_SPEC.md` §8 |
| Animation, 3 clips @ ~$1.13-1.31 | ~$3.39-3.93 | `COMIC_STRIP_NATIVE_SPEC.md` §8 |
| Build/score/SFX/caption/thumbnail/upload/website | $0 | all ffmpeg/PIL/offline, this document §7-13 |
| **Total (before reroll budget)** | **≈ $4.80-5.63 visual + $5.50-6.50 narration/audio ≈ $10-12/piece** | |

This sits well under the existing `$25/short` ceiling
(`LP-BUDGET`/`cost.check_budget`, enforced in code for the living-page lane)

doesn't yet.

**INV-20 (ask before spending) and the test-gate-before-batch discipline
apply to REAL production runs too, not only to experimentation.** The first
comic-strip-native piece run under this proposed workflow is itself a kind of
test — quote the estimated spend, get explicit OK, treat rerolls as a real
possible line item, and do not silently assume the $10-12 planning number
holds until it's been proven once on a real piece with real rerolls counted.

## 17. Episode-unit-of-work implications

If this piece is a short with a `parent:` long (or vice versa — the long
that will later spawn this technique's shorts), `pipeline/episode_state.py`
treats the pair as ONE unit, and three downstream stages need to account for
that rather than process this piece in isolation:

- **Thumbnail (§10):** `pipeline/thumbnails.py` already processes per-piece,
  but the long's thumbnail and its shorts' thumbnails should read as a
  visually coherent family (same title typography, same wordmark treatment)
  — nothing enforces this today; it is an eye-check, not a gate.
- **Upload (§11):** `build_upload_tracker.py` already wraps an episode's long
  + shorts in one release-campaign card (`epblock`), long first then shorts
  — this already works, no change needed, just confirm the `parent:` link
  was set at Stage 0 so this piece lands in the right campaign card instead
  of appearing as an orphaned standalone.
- **Website (§12):** SYNC-G7 (`release_check.py`) already FAILs a short in a
  cluster that has a long but carries no `parent:` — this is real
  enforcement, not just documentation; a comic-strip-native short skipping
  the Stage 0 continuity decision will get caught here, late and
  expensively, rather than never.
