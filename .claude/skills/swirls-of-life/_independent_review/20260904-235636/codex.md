# Independent review — codex (OK, 175s)

## Findings

1. **The alignment cache can silently be stale, defeating the entire timing premise.** The plan says the same call is “cached, idempotent” and that hashes make stale plans safe. In reality, `align()` reuses any parseable cache without checking whether it belongs to the current MP3 or transcript ([assembly_align.py](F:/slk/PycharmProjects/JesusInTheBible/pipeline/assembly_align.py:249)). If audio was re-synthesized before plan creation but the old cache remained, the plan would faithfully hash and use the wrong alignment. Require `force=True` immediately after `/voice`, or embed and validate source-audio/transcript hashes inside the alignment cache itself.

2. **“ElevenLabs forced alignment” is not a stable codebase fact.** The plan repeatedly names that backend, but `assembly_align` defaults to local `faster-whisper`, then maps/interpolates the known transcript onto ASR output ([assembly_align.py](F:/slk/PycharmProjects/JesusInTheBible/pipeline/assembly_align.py:27), [assembly_align.py](F:/slk/PycharmProjects/JesusInTheBible/pipeline/assembly_align.py:193)). Backend choice is environment-dependent. Interpolated or zero-duration words are weaker timing evidence than the plan’s “REAL word timestamps” language suggests. Record the backend/model in provenance and define acceptable alignment-quality checks.

3. **The plan’s central downstream integration is knowingly unresolved.** It first says “Nothing downstream changes,” but §8.1 admits “a precisely-timed score buys nothing unless the pages cut at the same times.” The real assembler still computes every slot proportionally ([swirls_assemble.py](F:/slk/PycharmProjects/JesusInTheBible/poc_living_water_ink_style_test/swirls_assemble.py:250), [swirls_assemble.py](F:/slk/PycharmProjects/JesusInTheBible/poc_living_water_ink_style_test/swirls_assemble.py:277)). This cannot remain a separate optional user decision. Introduce one canonical `unit_timing.json`, make both score generation and assembly consume it, and test the resulting page boundaries before adopting the stage.

4. **The proposed tooling does not exist.** §7 says “the derivation script asserts these,” but repository search finds no score-plan derivation, lint, rendering, or provenance-enforcement implementation—only this document and the manually authored episode-11 JSON. The current generator still posts a `music_v1` prompt and writes outputs directly ([generate_score_piano.py](F:/slk/PycharmProjects/JesusInTheBible/poc_living_water_ink_style_test/swirls_episode_11_where_are_the_nine/generate_score_piano.py:107)). The plan needs a named CLI/module, atomic output behavior, schema validation, tests, and explicit integration into the pipeline. “Same function, same cache file, no new code” seriously understates the implementation.

5. **The claimed “ONE beat map” would actually have multiple sources of truth.** Unit word counts already live in every episode’s `MANIFEST` ([episode.py](F:/slk/PycharmProjects/JesusInTheBible/poc_living_water_ink_style_test/swirls_episode_11_where_are_the_nine/episode.py:1004)); the proposal duplicates them into `score_composition_plan.json` and later into the design brief. Checking only that counts sum to 202 will not catch reordered units or compensating count errors. The lint must match each unit’s normalized exact text against the aligned transcript, not merely totals, and the manifest should derive from the shared timing artifact.

6. **The worked request contains contradictory style instructions.** §6.5 requires `"solo piano"` on every chunk, including F10 and the back cover, while those same chunks positively request violas, violins, cellos, and “soft strings underneath.” “Solo piano” conflicts with an accompanied piano-and-strings arrangement. Split the immutable identity into a common core plus pre-strings and post-strings variants.

7. **The smoke test does not test the mechanism being proposed.** A two-chunk, eight-second render checked only for vocals and drums says nothing about the risky parts: continuity across 12 short chunks, a semantic resolution on a boundary, ordered string entry, or whether long brace directions are followed. At 60 bpm, the 3.139-second opening is roughly three beats—an extremely short “section.” Before an 86-second render, test a representative 3–4-chunk excerpt containing unresolved music, the resolution boundary, and the strings transition.

8. **The automated musical verification is not credible.** §7 claims “an RMS/novelty sweep shows the resolution chord” and the first strings entry. RMS can find level changes, and novelty detection can find spectral/transient changes; neither establishes that a chord is a harmonic resolution or that the newly present instrument is strings rather than piano overtones. The API guarantees chunk durations, not sample-accurate realization of semantic instructions. The official documentation describes brace content as short inline cues and recommends broader direction in styles, weakening the plan’s assumption that “on the first beat” will be honored exactly. Use a human cue-sheet check for semantic events and limit automation to duration, silence, clipping, and coarse boundary-change evidence. [ElevenLabs composition-plan documentation](https://elevenlabs.io/docs/eleven-api/guides/how-to/music/composition-plans)

9. **Instrumental reliability remains a production single point of failure.** The plan correctly notes that `force_instrumental` cannot be used with a composition plan—the current API confirms this—but a single successful stochastic smoke render does not establish that future full renders will remain vocal-free. Every paid render needs a mandatory vocal/humming check and an explicit fallback to the proven `music_v1` prompt route. [ElevenLabs compose API](https://elevenlabs.io/docs/api-reference/music/compose/)

10. **Cost control is ordered incorrectly and lacks a ceiling.** “`/cost` pre-flight” appears as verification step 5, after both the smoke test and full paid render. Billing is simultaneously left unresolved in §9.5, with no expected credits, retry allowance, or maximum number of variants. Move cost verification before every metered call and state a hard budget covering the representative test, full render, and permitted retries. Official guidance says cost depends on track length and variant count, so “assumed per second like the prompt route” is insufficient. [ElevenLabs music cost guidance](https://elevenlabs.io/docs/help-center/product/core-capabilities/music/how-much-does-eleven-music-cost)

11. **Seed handling is underspecified and overstates repeatability.** §6.7 says to “pin one when re-rendering,” but the worked request has no seed and provenance does not record one. ElevenLabs only says identical seeds can improve consistency; exact reproducibility is not guaranteed. Define when a seed is created, persist it in the request, and never treat it as a reproducible build guarantee. [ElevenLabs compose API](https://elevenlabs.io/docs/api-reference/music/compose/)

VERDICT: REVISE
TOP FIXES:
1. Make alignment lineage and unit timing authoritative: force or hash-validate alignment, then have both score generation and assembly consume one shared timing artifact.
2. Implement and test the missing score-plan CLI, renderer, schema/lint rules, provenance enforcement, and per-render gates before calling this a pipeline stage.
3. Replace the inadequate smoke/measurement scheme with a representative resolution-to-strings test, human semantic cue verification, an explicit v1 fallback, and a pre-call spending ceiling.
