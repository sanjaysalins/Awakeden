# Independent review — claude (OK, 231s)

## Independent Review — Plan: "Fix the slow/expensive/error-prone content pipeline"

I checked several of this plan's factual claims directly against the repo rather than taking them on faith. Findings below.

**1. The "60 skills / 22 added in final 2 days" claim rests on the exact evidence type the plan itself calls unreliable, and the count is wrong.**
`.claude/` is entirely git-ignored (`.gitignore:29` — `.claude/	.claude/skills/animate`), confirmed via `git check-ignore -v` and `git ls-files .claude/skills | wc -l` → 0 tracked files. There is **no git history for this directory at all**, so "22 added in the final 2 days sampled alone" cannot have come from git log — it must be file-mtime reconstruction. That's the identical methodology the plan's own Retracted section calls "fragile — several episode folders get touched by unrelated later batch jobs" when dismissing the GATE-2/stale-episode claims. It wasn't re-applied here. Separately, the live count today is **94 directories** in `.claude/skills/`, not 60 — and a chunk of those (`design-an-interface`, `disk-space-cleanup`, `domain-modeling`, `git-guardrails-claude-code`, `grilling`, `dataviz`, `update-config`, `keybindings-help`, `simplify`, `fewer-permission-prompts`, `loop`, `schedule`, `claude-api`, `run`, `init`, `security-review`, `ask-matt`, `codebase-design`, `decision-mapping`, `diagnosing-bugs`, `edit-article`, `grill-me`, `grill-with-docs`, `handoff`) are generic Claude Code meta-skills, not "pipeline-specific" ones as claimed — so the actual pipeline-specific count and its growth rate are still unmeasured. The "zero wired into core pipeline code" half of the claim *does* check out (only hit was a docstring comment in `pipeline/concordance.py:17`), so that part is fine — but the headline growth number that motivates "skill/gate complexity is genuinely growing fast" wasn't re-verified by the red-team pass the way four other claims were.

**2. Step 2B proposes a manual checklist for exactly the failure class the codebase already has a proven deterministic-lint pattern for — and doesn't use it.**
CLAUDE.md's own locked decision on `panel_variety_lint.py` states plainly: *"This deterministic tag-check is a floor, not the ceiling... it caught 6 of 9 real collisions automatically."* That precedent exists because a *locked rule* (panel variety) kept getting violated in practice despite being written down — the fix was a $0 script, not tighter human diligence. Step 2B's three bullets (Kling/Seedance routing, character-ref attachment, NSFW-safe routing) describe the *same shape of problem* — a locked rule that Bronze Serpent's own build apparently didn't follow — and the proposed fix is "apply a pre-flight checklist... audit that the routing is actually applied before first render." I checked `longform/04_The_Bronze_Serpent/` for anything analogous to `panel_variety_lint.py` scoped to animator routing or character-ref presence — there isn't one. A checklist has no enforcement teeth; it depends on remembering to run it, which is plausibly how the original gap happened in the first place (the rule was already "locked" per CLAUDE.md before Bronze Serpent was built). This risks reproducing "discovered after a garbled result" instead of preventing it.

**3. Step 2B's before/after comparison has no control for the learning-curve confound.**
The plan measures the *next* living-sketchbook episode against the Storm/Bronze Serpent baseline (episodes 1-2 of a brand-new format) and treats improvement as evidence the checklist worked (Step 3: "If clearly better... write the checklist into CLAUDE.md"). But episode 3 of *any* new format should run faster than episodes 1-2 purely from the team having now built two of them — independent of any checklist. With n=1 and no held-out episode built *without* the checklist for comparison, the plan can't actually attribute a wall-clock improvement to the intervention vs. ordinary practice effect. For a plan whose stated premise is "scientific, numbers-backed," this is a real gap in Step 3's decision rule.

**4. Step 2A understates the actual work, and its "follow the existing pattern" citation points at the wrong file.**
I read `pipeline/cost.py:82-90` (`record()`, the actual reusable spend-ledger writer referenced throughout the file map as the "reuse, don't duplicate" pattern) — its ledger write is a bare `with LEDGER.open("a", ...)`, **not** try/except-wrapped. The try/except-wrapped writes the plan is citing live in `cost_status.py` (a separate statusline hook script), not in the shared `pipeline/cost.py` module. If `pipeline/stage_log.py` is modeled on `pipeline/cost.py` (the natural sibling, same directory, same "ledger" concept) rather than `cost_status.py`, it will silently inherit an unwrapped write and violate the plan's own "failure to write must never block the pipeline" requirement. Worth being explicit about which file is actually being copied. Separately, threading 6 new `record()`-style calls into `handoff.py`, `visual_handoff.py`, `visual_runner.py`, `assembly_handoff.py`, `assembly_runner.py` is a real multi-file change, understated by "one small, best-effort append-only logger" — not a blocker, just scope honesty.

**5. Step 2A's own verification method repeats the tool it's replacing.**
Verification for Step 2A is "spot-check by hand against known milestone file mtimes" — but mtime-based reconstruction is precisely what Step 2A exists to stop relying on (per the plan's own Context section: "fragile"). A stronger check would diff `stage_timings.jsonl` entries against the write-point commit's own timestamp or an existing timestamped field in `narration.creation.json`/`scene_plan.json`, not raw mtimes.

**What I confirmed holds up:** Step 0's claims are accurate — `git show d6d2e03` matches the described file set, `.gitignore` additions are present, `data/.watcher_status.json` currently reads `{"state": "ok", "count": 0}`, and `.agent_bridge/_stale_cleared_20260801/` exists with the archived content. STATE.md/RESUME.md really are current (2026-08-01 top entries confirmed) — the "not stale" retraction is correct. The "ask before spending," Kling/Seedance routing, character-ref, and NSFW-fallback rules the plan cites as "existing locked rule[s]" do genuinely exist in CLAUDE.md as described. No duplicated tooling — `stage_log.py` fills a real gap (cost.py tracks spend, not elapsed wall-clock).

VERDICT: REVISE
TOP FIXES:
1. Re-verify the "60 skills / 22 in 2 days" growth claim with a method that doesn't rely on mtimes for an entirely git-ignored directory (e.g., re-run the red-team specifically against this number), and separate "generic Claude Code skill" from "pipeline-specific skill" before recomputing.
2. Replace or supplement Step 2B's manual pre-flight checklist with a $0 deterministic check (grep `scene_plan.json`'s routing field against the actually-rendered animator per panel, character-ref presence, NSFW-flagged stills) — the codebase already proved this pattern works for the same class of problem via `panel_variety_lint.py`.
3. Fix Step 3's decision rule to account for the learning-curve confound — either don't treat one improved episode as proof the checklist worked, or explicitly name "faster than baseline AND still slower/equal to a mature-format episode's 1.5-2h" as the bar, not just "clearly better than Storm/Bronze Serpent."
